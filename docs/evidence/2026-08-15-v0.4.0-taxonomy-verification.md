# Version 0.4.0 taxonomy verification — 2026-08-15

## Scope

This evidence covers bounded ZenMoney category creation, allowlisted updates, and reversible retirement. It contains no category names, IDs, transactions, balances, credentials, or receipt data.

## Offline verification

`npm run check` passed on Node.js 22.22.0:

- 11 test files and 35 tests passed;
- TypeScript typecheck passed;
- production ESM bundles built;
- MCP stdio smoke passed with 22 tools;
- the private child backend started with synchronization disabled;
- repository validation passed with 15 required files checked;
- `npm audit --omit=dev` reported zero vulnerabilities.

The taxonomy suite proves:

- preview calls issue no `tags_create` or `tags_update` write;
- create/update/retirement applies are exact, verified, and process-idempotent;
- a stale category version blocks before the write transport;
- sibling-title normalization, control-character rejection, one-level parent depth, active-parent rules, and explicit retirement fail closed;
- mutation preview refuses a taxonomy beyond the complete 500-record safety bound rather than checking a truncated tree;
- retirement refuses an active parent and rechecks child state immediately before apply;
- retirement leaves a representative historical transaction reference unchanged;
- retired categories are excluded from normal active-category lists and remain available for explicit taxonomy inspection.

`quick_validate.py` passed for both the receipt-categorization and category-review skills after their workflows were updated for the new tools and receipt-informed suggestions.

The explicit skill refresh test passed for both paths: recognized ZenMoney skills update from the clone, while an unrecognized same-named directory blocks before any partial refresh. The maintainer's installed receipt/category/savings skills were refreshed, byte-compared with the clone, and the changed skills validated successfully.

## Live read-only verification

`npm run doctor:live` passed:

- version 0.4.0 build detected;
- macOS Keychain credential available without exposing its value;
- Codex registration points to this build;
- ZenMoney synchronization succeeded;
- 79 active categories were counted without printing records or making changes.

`npm run test:live-readonly` passed and additionally verified that every active category returned:

- an integer optimistic-concurrency version;
- boolean income, expense, budget, and retirement fields;
- a hierarchy compatible with ZenMoney's one-parent limit.

The same read-only run generated create, update, and retirement previews against the live taxonomy, verified that each returned a confirmation boundary, discarded the tokens, and called no apply tool. The synthetic create title existed only in process memory and was never sent as a mutation.

An initial preview probe exposed a valid live category whose budget and visibility flags do not move together. The implementation removed an unsupported coupling assumption and retained only the documented independent booleans plus the explicit both-hidden retirement boundary. The final live preview run then passed.

The implemented shape is consistent with ZenMoney's published [`Tag` entity and `/v8/diff/` contract](https://github.com/zenmoney/ZenPlugins/wiki/ZenMoney-API#tag). The published tag schema contains no archive field, so the connector implements reversible retirement through visibility/budget flags instead of claiming archive semantics.

## Not verified

No live category create, rename, reparent, retire, or restore was run. This task authorized repository implementation but did not authorize mutations to the user's real financial taxonomy. A future synthetic live test needs fresh explicit authorization, exact preview logs, deterministic cleanup/restoration, and confirmation that no test category remains.

Category hard deletion and bulk historical consolidation are not implemented or verified. They remain tracked by `F-016`, which depends on the crash-safe operation journal in `F-005`.

Cross-session receipt evidence storage is not implemented. Receipt-informed grouping in v0.4.0 is limited to artifacts visible to the host in the current session; opt-in structured memory with inspect/purge controls is tracked by `F-017`.
